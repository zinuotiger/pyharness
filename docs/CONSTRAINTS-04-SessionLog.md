# CONSTRAINTS-04 — 会话日志约束

> 类型: 硬约束 | 权威: PRD-Core.md §3 + EVENT-SCHEMA.md + DIS-CORE.md §3
> 适用: session/persistence 模块全部实现,事件溯源是项目灵魂

## 1. 不可变性与追加
| # | 约束 | 说明 |
|---|------|------|
| S-01 | 只追加 | 已写事件不可修改不可删除;程序无"改历史"代码路径 |
| S-02 | 单一真源 | 消息历史从日志派生(derive reducer);禁止内存消息列表作为第二真源 |
| S-03 | 事件信封完整 | 每事件含 seq/type/timestamp/session_id/payload;seq 单调递增 |
| S-04 | 强同步三类 | 仅三类事件强制落盘(见 EVENT-SCHEMA.md §8);其余批量异步 |

## 2. 写入纪律
| # | 约束 | 说明 |
|---|------|------|
| S-05 | 先校验后写入 | 事件格式非法 → 拒绝写入(EVT-105),坏数据不进日志 |
| S-06 | 原子写 | 临时文件+rename;写一半断电不损坏已提交事件 |
| S-07 | flush 策略明确 | 强同步事件即时 flush;普通事件攒批 |
| S-08 | 损坏检测 | 读取时检测截断/非法行 → repair 或拒绝加载(格式版本不符拒读) |

## 3. 派生态
| # | 约束 | 说明 |
|---|------|------|
| S-09 | 派生纯函数 | derive reducer 无副作用,同输入必同输出;禁止 reducer 内调 LLM/IO |
| S-10 | 回放等价 | 从日志重建的上下文与当时一致;回放是调试与审计的基础 |

## 4. 如果违反会发生什么
- 违反 S-01(改历史): 审计失效,回放结果与真实过程不符,出问题无法定位
- 违反 S-02(双真源): 内存历史与日志不同步 → 重启后 AI"失忆"且无法解释
- 违反 S-06(非原子写): 断电 → 日志截断损坏 → 会话不可恢复

## 5. 验收
- [ ] 不变量测试: append 后事件内容不可变;无 delete/update API
- [ ] 重启恢复测试: 关程序重开,从 JSONL 重建上下文与关闭前一致
- [ ] 损坏日志测试: 人为截断文件 → 加载器报错或 repair,不静默吞数据
- [ ] reducer 纯函数测试: 同输入两次调用输出 byte 级一致

## 6. 深度场景推演:如果违反会话日志约束会怎样

### 场景 6.1:为省事直接存"组装好的消息列表"(违反 S-02)
**根因**: "derive 太麻烦,内存里直接维护 messages 数组,每次 append 一份不就行了"。
**连锁后果**: ① 内存消息列表与 JSONL 日志两份状态 → 某次漏同步(比如工具结果先更新了内存没写日志) → 重启后从日志恢复的上下文与崩溃前不一致,用户困惑"AI 怎么忘了刚才的事";② 回放只能回到"日志版本",无法解释线上行为(日志没有工具调用中间态);③ 加功能(compaction/编辑/分叉)时要在两处实现,复杂度翻倍,迟早不一致。
**正确做法**: 内存只有"日志 + 增量派生缓存",任何状态变更唯一入口是 append;AI 看到什么 = 从日志 derive 出什么,永远一致。

### 场景 6.2:允许修改历史事件(违反 S-01)
**根因**: "用户说错了话想删掉重说,直接改日志不就行了"。
**连锁后果**: ① 审计价值归零——日志不再可信,无法证明"AI 当时真的调了那个工具";② seq 链断裂,后续事件引用(provenance)错乱,回放崩溃;③ 一旦开了"可以改"的口子,compaction/编辑功能都会走修改路径,append-only 的纯洁性失守;④ 面试被问"事件溯源为什么只追加",你说"为了审计",但代码里能改 = 自相矛盾。
**正确做法**: 用户修正 = append 一条 supersede/编辑事件标记旧事件作废,历史物理不变,逻辑上以新事件为准。

### 场景 6.3:flush 全异步,强同步事件也攒批(违反 S-04/S-07)
**根因**: "性能优先,写盘越少越好"。
**连锁后果**: ① 强同步事件(用户消息/工具结果)没落盘就继续跑 → 进程崩溃 → 这轮对话永久丢失;② 用户以为 AI 回复了(内存里有),重启后全没了;③ 工具执行了但结果事件丢了 → 回放时工具副作用存在但日志无记录 → 无法审计(钱花了/文件删了没记录)。
**正确做法**: 强同步三类事件(见 EVENT-SCHEMA.md §8)同步写盘后才继续;普通事件(中间 chunk)可批量。性能损失可接受——正确性优先。

## 7. 事件日志验收 GWT(核心三条)
- Given 一条事件已 append, When 尝试修改或删除, Then API 不存在/抛错,文件内容 hash 不变
- Given 程序运行中强制退出, When 重启加载, Then 从 JSONL 重建上下文,与退出前 AI 所见一致(强同步事件不丢)
- Given 日志文件被截断损坏, When 加载器读取, Then 检测损坏位置,可选 repair 或拒绝加载(版本不符拒读),不静默吞数据

## 8. 与下游模块的契约
- **llm 模块**: 请求上下文 = session.derive_messages(),禁止直接读日志文件拼 prompt
- **tools 模块**: 工具执行前后的事件( tool-call / tool-result )由 session.append 统一落盘,工具模块不自己写文件
- **persistence**: 只有 session 模块知道"何时强同步 flush";persistence 只提供 append/read/repair 原语
- **compaction(第 5 阶段)**: 压缩 = append 一条 compacted 事件 + 遮蔽旧事件(surface 语义),物理日志仍只追加
