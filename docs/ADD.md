# 1 概述

PyHarness 的全部架构约束可压缩成一句话:**单进程插件架构 = 事件溯源真源(JSONL append-only)+ 能力 seam 三件套 + guard 单调拒绝 + 自研插件总线 + 八模块不可换脊柱,66 项功能沿 6 个"每阶段可运行"的里程碑生长**。每个词都是一次取舍,理由与代价即本文档:ADD 记"决策"、PRD-Core §4 记"原则"、TECH-ANCHOR 记"边界",构成「决策→原则→边界」链条。12 条 ADR 中,ADR-001/002/003/009/005/008 对应 PRD 六原则 1-6,其余为支撑性决策(总线自研/存储分工/降级协议/脊柱边界/错误码契约/外壳形态)。每条 ADR 固定七节:元信息、【背景/决策/后果/违反它的后果/备选方案对比/关联】,违反后果节必写具体失败场景;压倒性约束是"从零可讲、可逐行审查、可演示","引黑盒换省事"的方案因此被否。

# 4 ADR 正文

### ADR-001:事件溯源——append-only JSONL 为会话唯一真源,不用内存消息列表

**状态**:已接受 | **日期**:2026-09-06 | **落点**:阶段1(F007/F009/F011),波及全部 6 阶段 | **原则映射**:PRD 原则 1

**背景**:一次会话产生一串事实:用户输入、LLM 请求/响应(含 tool_calls 原始 JSON)、工具执行与结果、guard 判定、审批、token 用量、错误。循环要"上下文",调试要"现场",审计要"谁在何时干了什么",崩溃后要"还记得"。最直觉的实现是进程内维护一份 message list:append 后用,持久化靠定时 dump。但循环里状态被多处读写(循环驱动器、工具回填、上下文重建、UI 推送),内存列表一旦与落盘副本分叉,无人能判定谁对——"日志说 A,内存说 B"是调试噩梦。约束:单进程、无 PG/Redis、可回放/可审计是第一卖点,必须从阶段1 就是真源。

**决策**:采纳事件溯源:一切会话事实编码为事件(Envelope 含 seq/type/payload/ts/actor/trace),全系统只有 `session.append(event)` 一个写入口——校验(信封字段/seq 连续/类型已注册,违规拒写 EVT-100/101/102/106)→ 分配 seq → 经总线分发 → persistence 追加进 JSONL。**文件是唯一真源**;内存只保留可丢的 history_cache(append 即失效);`derive_history()`/`rebuild_from_log()` 是派生唯一实现;LLM 上下文、UI 时间线、token 汇总全是日志投影,禁止任何模块维护第二份状态。

**后果**:收益——①回放:bug 拿日志从头重演即是现场;②审计:工具调用/审批/guard/降级都是一行带 actor+trace 的事实;③恢复:文件即状态,崩溃扫尾截半行重建(阶段6 F060 根基);④一致性:无第二份权威状态,"内存说 A 日志说 B"结构上不可能。代价——①读侧 O(n),老会话查询交给 SQLite 投影(ADR-006),不改真源形态;②文件增长靠 compaction 管理旧段(F060);③单一写入口需纪律,任何"先改内存再落盘"的捷径都会破坏语义,靠 INV 测试拦截。

**违反它的后果(具体场景)**:若改用"内存列表 + 定时 dump":①进程被 kill/OOM,最近一个 dump 窗口的事件全丢,重启后 AI 记忆与用户所见不一致,且无对照物、无人察觉;②"14:02 那次 delete_file 谁触发、参数是什么"无解——没落盘=没发生,审计与面试都答不出;③复现 bug 只能人肉回忆,无法原样重放那次会话;④全量快照越写越贵,dump 与内存间永远有半个窗口的不一致,恰是出事最多的窗口。若改用 SQLite 单表存消息:可查但不可人读、回放要写 SQL 导出——真源被数据库格式遮住,分工论证见 ADR-006。

**备选方案对比**:

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| 内存消息列表 + 定时 dump | 实现最直白,读写快 | 丢窗口/无审计/快照重写放大/双份状态分叉 | ❌ |
| SQLite 单表存会话消息 | 有索引可查询,事务安全 | 真源不可人读、append 语义被事务复杂化、回放/备份绕 SQL | ❌ |
| JSONL append-only 文件为唯一真源 | append O(1)、可 cat/grep/回放、备份=copy、审计成行 | 读侧 O(n),需查询投影补偿 | ✅ 采纳 |

**关联**:ADR-006(查询投影分工)、ADR-002(事件经总线分发,总线不落盘 F001,落盘由日志订阅者完成)、ADR-011(拒写即错误码 EVT-1xx)、PRD-Core §3.5(seq/reducer)/§3.6(JSONL 物理格式)/§4.1、阶段6 F060。

### ADR-002:能力 seam 三件套——Definition/Provider/Consumer 为何分离

**状态**:已接受 | **日期**:2026-09-06 | **落点**:阶段1(F008/F026)+阶段3-6 全部能力项 | **原则映射**:PRD 原则 2

**背景**:66 项功能绝大多数以外围能力形态挂 ctx.*:工具类(文件读写/列目录/Web 搜索/Web 抓取/subprocess/PTY)、编排类(plan/queue/subagent/workflow/jobs/schedule)、会话类(fork/compaction/FTS/repair)、存储域。这些能力的共性:既要被 LLM 通过"声明"发现和调用(名字、参数 schema、描述、危险标记),又要被核心脊柱以统一协议消费(校验→guard→审批→计量→执行→结果检查→留痕)。若把"是什么/怎么实现/谁来调用"揉进一个对象:测试被迫造真文件、换实现(本地↔域)要改所有调用点、脊柱对实现产生反向依赖;若不建统一 seam 各写各的消费代码,脊柱 tools 会被几十个 if 淹没。

**决策**:每种外围能力拆三件套 seam——①Definition(不可变契约:name/描述/参数 schema/危险标记/guard 钩子/审批要求;给 LLM 看、给校验器用、供审计对比的是同一份);②Provider(实现与装载生命周期,可整体替换,不携带消费逻辑);③Consumer(消费点:校验→guard→审批→计量→执行→结果检查,不关心实现是谁)。三件在总线注册表按 name 登记;脊柱只 import 契约层;ctx.*(ctx.tools/ctx.agent/ctx.session/ctx.storage/ctx.sys)是消费端统一门面,能力间禁止互相 import 实现,只能经 ctx 注入。新能力只需写 Definition+Provider 即自动获得校验/guard/审批/计量/留痕——这些能力全在消费协议里,不在实现里。

**后果**:收益——①依赖倒置:脊柱依赖抽象不依赖实现,外围增长不触碰核心;②可插拔:换 Provider(本地↔域、假实现↔真实现)不碰 Consumer,这正是"外围可插拔"的机制载体;③可测试:注入假 Provider 即可单测消费协议,无需真实文件系统/网络;④契约与实现解耦:LLM 看到的 schema 与真实执行是两份独立工件,可审计"模型说了什么 vs 实际执行了什么"(INV-06 逐字段断言)。代价——①三件套样板:每能力三份工件,抽象多一层;②纪律:Provider 禁止反向 import Consumer,只能经 ctx 注入;③Definition 发布给 LLM 后不可随意改字段,变更走版本演进(PRD §3.8)。

**违反它的后果(具体场景)**:若揉成单一 Tool 类:①阶段3 每加一个工具都改核心注册表类型定义——违反开闭,脊柱被外围污染(ADR-010);②单测 read_file 被迫造真文件、测 Web 抓取被迫联网,测试变脆,最后没人写;③storage 本地换"域实现"时所有调用点跟着改,可插拔名存实亡(TECH-ANCHOR 五主线之一);④契约与实现混在一起,实现者把描述写成实参名,模型按描述传参、执行层按签名收参,校验错配且审计无 raw_args 对照;⑤面试只能答"加一个类再改注册表",讲不出依赖倒置与开闭——恰是能力 seam 最该讲深的叙事。若只拆两层(无统一 Consumer):各调用点重写校验/guard/计量,同一能力行为不一致,guard 漏挂即安全漏洞(ADR-003)。

**备选方案对比**:

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| 单一 Tool 类(声明+实现+消费混合) | 文件少、直觉 | 核心被外围污染/测试要真实现/契约不可审计 | ❌ |
| 两层(接口+注册表,无统一 Consumer) | 比一层清晰 | 消费逻辑散落,校验/guard 各点重写且易漏 | ❌ |
| 三件套 seam:Definition/Provider/Consumer | 依赖倒置+可插拔+可测试+契约可审计 | 每能力三份工件,需纪律约束依赖方向 | ✅ 采纳 |

**关联**:ADR-003(guard 作为消费协议横切,挂在 Definition 钩子上)、ADR-009(Definition.schema 即"先验后跑"的校验源,单一来源不重复维护)、ADR-004(总线注册表登记三件套)、ADR-010(脊柱/外围边界判据)、PRD-Core §2.3/§4.2、F001/F008/F026。

### ADR-003:guard 单调拒绝——安全只紧不松,不提供 allow

**状态**:已接受 | **日期**:2026-09-06 | **落点**:阶段1(F014/F015/F023),阶段3/5 高危工具全部依赖 | **原则映射**:PRD 原则 3

**背景**:危险能力(删文件/执行命令/外发网络/读凭据)执行前必须把关。业界常见两招——黑名单(默认放行)与"信任模式"(为体验放行)——在 agent 场景都是致命错误:LLM 可被第三方内容注入,攻击面是"模型+工具+外部内容"整条链;安全策略一旦存在可放宽的开关,一次配置失误或注入成功即永久放大攻击面。约束:PRD 原则 3、F014/F015、scope 域(F023);guard 判定必须可审计(事件留痕)。

**决策**:guard 采用单调拒绝模型——一叠 guard 检查(作用域边界/危险工具标记/凭据路径/预算)沿 Definition 钩子依序执行,每层都可判"拒绝"或"需审批",但**没有任何一层、任何开关能对已被拒绝的调用放行**;唯一人工放行路径=审批(approval):逐次有效、审批人/时间/参数全部留痕。配置默认 deny:未知工具/越界路径/未列入作用域的命令一律拒绝;不提供"全局 allow"、不提供"开发者信任模式"。scope 作用域预授权只是预先声明合法集合,任何一层 guard 仍可拒绝,不存在"声明过就绕过 guard"的通道。

**后果**:收益——①安全只紧不松:配置漏了/配错方向都=拒绝,错误方向安全;②注入即使成功,破坏被限制在 guard/审批/预算的笼子里;③审计线完整:每次拒绝与审批都是事件,可回答"谁批了哪一次、什么参数";④面试"如何保证不误删"有确定答案:默认拒绝+逐次审批留痕。代价——①合法高频操作偶尔被打断,用作用域预授权缓解;②guard 链顺序与钩子判定需测试覆盖,单调性由 INV 断言(代码中不存在任何 allow 路径)。

**违反它的后果(具体场景)**:若提供 allow 开关或黑名单默认放行:①用户开"信任模式"后一次注入让模型调 delete_file,黑名单只拦已知命令名,新工具=默认放行——文件没了,审计只能答"当时开着信任模式";②单调性破坏后 guard 链形同虚设:攻击者只要找到任一放行点即可绕越其上全部检查——安全强度=最松一环,不是最严一环;③"为什么能删?"的追问变成产品经理与开发的互相甩锅,因为放行是全局配置,不是逐次决策;④面试安全追问"如何保证不误删"时,黑名单方案的唯一诚实回答是"没有保证,因为默认放行"——单调拒绝下回答是确定的:默认拒,除非逐次审批留痕。

**备选方案对比**:

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| 黑名单,默认放行 | 体验顺滑,几乎不打断 | 注入即默认执行;新危险=未拦截;强度=最松一环 | ❌ |
| 白名单默认拒绝(无审批通道) | 最安全 | 合法操作全被挡死,不可用 | ❌ |
| 白名单默认拒绝 + 逐次审批留痕(单调拒绝) | 安全只紧不松+可人工放行+可审计 | 偶尔打断,需作用域预授权缓解 | ✅ 采纳 |

**关联**:ADR-002(guard 钩子挂 Definition,消费协议横切)、ADR-009(参数校验在 guard 之前,两道闸缺一不可)、ADR-005(同进程=拒绝与审批同信任域即时生效,无策略下发延迟窗口)、PRD-Core §4.3、F014/F015/F023、阶段5 sandbox/workspace(F054-F055)。

### ADR-004:自研轻量插件总线,不引 pluggy 等现成框架

**状态**:已接受 | **日期**:2026-09-06 | **落点**:阶段0(F001-F006) | **原则映射**:PRD 禁止表"现成插件框架"条目 + 原则 2/5

**背景**:阶段0 要交付"插件总线地基":事件分发(emit/subscribe)、注册表(插件/工具/能力)、热插拔(install/uninstall/激活)。Python 生态有成熟方案:pluggy(最流行的 hook 框架)、importlib.metadata entry points(跨包动态发现)、或自研注册表总线。约束:依赖总数 ≤15;PRD 禁止表明令排除现成插件框架(pluggy 等)——总线机制是面试"一切皆插件"的主战场;单进程显式注册足够,无需跨包动态发现。

**决策**:自研轻量总线(`pyharness/bus/`,约数百行):EventBus(订阅分发,按订阅序同步/异步调用 handler,handler 异常封装 EVT-103 不中断他人,背压满拒新不丢旧 F005)+ Registry(插件/能力注册表,类型 schema 预注册,未知类型拒投 EVT-102)+ 生命周期(install/uninstall/activate,卸载脊柱模块返回 BUS-002)。事件经总线分发给订阅者后,由日志订阅者负责落盘——**总线不落盘**(F001),真源纪律归 persistence(ADR-001)。能力三件套(ADR-002)经 Registry 登记;热插拔的语义=从 Registry 摘除+停止该插件订阅,事件即刻不再投递。

**后果**:收益——①学习价值:从 emit 到订阅者隔离(EVT-103)到热卸载每行可讲可追问,是"自研 Cordis 等价物"的意义所在;②控制面小:只需注册/分发/热插拔三条路径,pluggy 的 entry-point 发现、wrapper 排序等机制全用不上;③依赖面小+零间接依赖,符合 ≤15;④可调试:投递统计/订阅顺序/异常隔离都是自己的代码,断点即真相。代价——①分发顺序/重复注册/异常隔离等边界要自测(阶段0 验收覆盖);②无现成生态:未来若需跨包动态发现,再在 Registry 加 entry-points 适配器,接口已预留,现在不引入。

**违反它的后果(具体场景)**:若改用 pluggy:①面试被问路由/热卸载/异常隔离只能答"pluggy 干的"——机制是黑盒,而本项目第一价值是讲深;②hookspec/wrapper 语义是学习与排障成本,66 项没有一项需要它;③直接违反 PRD 禁止表,评审第一轮即不过。若完全不要总线、硬编码装配:①每新增能力都要改 core 装配代码,脊柱被外围污染(ADR-010);②"可插拔"退化成"可改源码",热卸载演示不存在;③能力间悄悄直接 import 无人拦截,卸载一个插件拖垮另一个的隐患第一天就埋下。若用 entry-points 动态发现:显式注册已够用,动态发现引入"装没装上"的隐式状态,演示与测试更难确定环境。

**备选方案对比**:

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| 硬编码 if-else 装配 | 零抽象 | 新能力改核心/不可插拔/无热卸载 | ❌ |
| pluggy 等现成框架 | 成熟、生态全 | 禁止表明令+机制黑盒+死重功能用不上 | ❌ |
| importlib entry-points 动态发现 | 跨包自动发现 | 单进程不需要,隐式状态害调试 | ❌ |
| 自研注册表总线(数百行) | 机制全透明可讲深/控制面小/依赖面小 | 边界行为需自测 | ✅ 采纳 |

**关联**:ADR-002(注册表登记三件套)、ADR-001(事件经总线但总线不落盘)、ADR-005(总线=单进程内唯一通信通道)、PRD-Core §5.1(F001-F006)/§2.1、BUS-002/EVT-102/103。

### ADR-005:单进程插件架构,不做微服务/多进程

**状态**:已接受 | **日期**:2026-09-06 | **落点**:全局(阶段0-6),阶段4 编排尤甚 | **原则映射**:PRD 原则 5

**背景**:架构分四层(总线地基/脊柱/外围/外壳),66 项里有编排(jobs/schedule/子 Agent/workflow)与系统(subprocess/PTY/sandbox)能力。自然的诱惑:子 Agent 拆独立进程、jobs 走消息队列、Web 独立部署。但约束是硬的:禁止 Docker/PG/Redis/跨进程微服务;单机个人工具场景;事件 seq 必须全进程单调(原则 1 前提);面试要"一条命令跑起整个系统"。

**决策**:单进程单事件循环:四层同进程,层间通信=函数调用+事件投递,无网络、无序列化边界、无独立部署单元。子 Agent/jobs/schedule/workflow 全部是**协程级并发**,共享主会话事件日志与 seq 分配器(INV-07 断言:全库进程数=1,无 multiprocessing/跨进程 RPC)。唯一的多进程出口是显式工具 subprocess/PTY(F052/F053),且必须过 guard、结果作为工具事件回流;高危隔离交给 sandbox 子进程(F054-F055),同样受 guard 管辖。FastAPI Web 壳(桌面模式由 pywebview 内嵌)单 worker 同进程(ADR-012)。

**后果**:收益——①真源闭环:事实同进程产生、落同一日志,无跨服务顺序难题(seq 空洞只可能来自本地崩溃,repair 可处理);②guard/审批即时:拒绝与批准同信任域生效,无策略下发延迟窗口(单调性在进程内才有瞬时保证);③部署即运行:`python -m pyharness` 即完整系统;④调试友好:断点/日志/回放一体。代价——①单机扩展受限,个人工具场景足够;②进程内插件死循环拖慢全体:以超时(F025)+轮数/预算闸(F032)兜底,高危隔离交给受 guard 的 sandbox 子进程。

**违反它的后果(具体场景)**:若把子 Agent 拆成独立进程走 HTTP:①子进程事件无法共享主会话的 seq 单调序列——两个事实源,原则 1 直接破,回放时子 Agent 段与主会话对不上号;②主进程 guard 拒绝某操作时,子进程可能已在执行同类操作(策略不同步),原则 3 破——单调拒绝只在单信任域内成立;③引入进程管理/端口/鉴权/序列化,直接撞禁止表,本地起 N 个进程,面试叙事从"事件溯源内核"滑向"调了一堆进程";④jobs 若上消息队列:背压/重投/死信/持久化一整套基建,且队列事件与 JSONL 真源谁是老大说不清。多进程 worker 池同理:分发与状态同步与"单一真源"天然冲突——worker 内存态无法进日志投影。

**备选方案对比**:

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| 微服务拆分(子 Agent/队列独立部署) | 水平扩展、故障隔离 | 双事实源/策略不同步/撞禁止表/复杂度爆炸 | ❌ |
| 多进程 worker 池 | 利用多核 | 状态与 seq 难共享,与事件真源冲突 | ❌ |
| 单进程插件架构(协程并发+受 guard 的 subprocess 出口) | 真源闭环/策略即时/部署即运行 | 单机扩展受限,需超时预算闸兜底 | ✅ 采纳 |

**关联**:ADR-001(seq 单调的前提是单进程)、ADR-003(单调拒绝同信任域)、ADR-004(总线=进程内通道)、ADR-012(Web 同进程)、PRD-Core §4.5/F043-F051。

### ADR-006:JSONL 存会话事件、SQLite 只做查询投影——存储分工

**状态**:已接受 | **日期**:2026-09-06 | **落点**:阶段1(F011)+阶段5(F057 会话查询/F059 compaction) | **原则映射**:PRD 原则 1(真源唯一)落地形态

**背景**:存储侧有两个需求:①写入——每次消息/工具调用都要落盘,事件频繁,要求 append 廉价、文件可人读、可回放、可审计;②查询——老会话全文检索(阶段5 演示 `pyharness search`)。SQLite 已因 FTS5 全文检索入选,于是出现一个看似省事的诱惑:事件直接写 SQLite,一个库同时解决持久化与查询。约束:原则 1(真源唯一)、单进程文件存储即可、审计与面试演示要求"能 cat 的本子"。

**决策**:分工而非二选一——**真源 = JSONL append-only 文件**:写入路径 `session.append → persistence 追加`,append O(1),无事务/锁竞争;文件可 cat/grep,回放=从头读,备份=copy 文件。**SQLite FTS5 库只做查询投影**:一个总线订阅者把事件增量导入查询库(会话元数据+文本块+FTS 索引);查询库与真源单向(文件→查询库),可随时删除并用 `rebuild_from_log()` 重建,永不回写真源;compaction 压缩旧段后按同规则重新投影;一致性不靠事务,靠"可重建"兜底。

**后果**:收益——①写入廉价且语义纯净:append 就是 append,崩溃恢复=扫尾截断半行,不需要 WAL/事务语义;②真源人读保真:排障、审计、面试演示都直接 cat 日志,事件溯源的第一卖点不被数据库格式遮住;③查询域独享 SQLite 的索引/FTS5 能力,各取所长;④查询库损坏不影响真源,重建即愈。代价——①双写路径:多一个总线订阅者与导入逻辑;②双份磁盘占用;③需要纪律:任何代码不得把查询库当真源写回(查询库永远派生)。

**违反它的后果(具体场景)**:若事件直接进 SQLite:①排障与演示变成"先写 SQL 再解释",丢失可 cat 的本子与回放直观性,审计要导出再 grep;②高频事件变事务写,崩溃恢复依赖 WAL 而非"扫尾截半行",repair(F060)被存储引擎绑架;③备份从 copy 变成 dump,轮转都绕;④FTS 索引与事件本体耦合在同一写路径,写放大。反之一头扎进"全 JSONL 不建库":阶段5 的老会话全文检索每次 O(全量顺序扫描),上千事件后 `pyharness search` 卡顿到不可演示——查询域的需求是真实需求,不能为了"少一个订阅者"牺牲它。

**备选方案对比**:

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| 全 JSONL,查询也顺序扫 | 单一存储最简 | 全文检索 O(n),老会话查询不可用 | ❌ |
| 全 SQLite,事件直接入库 | 一个库两用 | 真源不可人读/append 语义受损/回放审计绕 SQL | ❌ |
| JSONL 真源 + SQLite 查询投影(单向可重建) | 两域各取所长/真源纯净/查询可删建 | 双写路径+双份磁盘 | ✅ 采纳 |

**关联**:ADR-001(真源纪律)、ADR-004(导入订阅者挂总线)、PRD-Core §3.6/F011/F057/F059、阶段6 F060(repair 重建投影)。

### ADR-007:降级链主 DeepSeek 备 qwen-max——OpenAI 兼容格式单一客户端

**状态**:已接受 | **日期**:2026-09-06 | **落点**:阶段1(F012 基础)+阶段2(F027-F033 加厚) | **原则映射**:PRD §2.2 llm 模块职责

**背景**:llm 模块要求主模型 DeepSeek、备用 qwen-max,自动降级(演示场景:主模型 401 自动切备)。两家均提供 OpenAI 兼容端点:DeepSeek 官方 API 与 dashscope 的 compatible-mode 都走 `/v1` 形态。实现候选:两家官方 SDK、原生 HTTP 给每家写适配、openai SDK 单客户端换 base_url。约束:依赖 ≤15;降级必须是"配置级"而非"代码级"——新增第三家模型不应改 llm 模块代码;流式/工具调用解析/用量计量只允许写一份。

**决策**:采用 openai SDK 单客户端(AsyncOpenAI):模型=(base_url, api_key, model) 三元组;降级链=按序换三元组、重发同一请求体(构造与解析完全复用);统一解析层(pydantic),流式 chunk、tool_calls 原始 JSON、用量全归一;厂商扩展字段留透传槽(如 reasoning_content 原样入 raw 字段,不进标准字段);超时三档(10s/60s/180s,F025)与重试在客户端层统一;降级判定按错误码(401/429/超时)而非异常文本(ADR-011)。

**后果**:收益——①一份客户端覆盖 DeepSeek/qwen-max/任何 OpenAI 兼容模型:演示"加第三家"只需加配置行,llm 零改动;②流式、用量计量、重试只写一次,三家共用;③降级链是数据驱动遍历,不是 if-else 堆厂商;④兼容格式=降级链地基,可讲"换主模型不换代码"。代价——①引入 openai 库一个依赖(计入 ≤15);②依赖厂商"兼容"承诺,字段缺失在解析层打补丁;③厂商特定能力走透传槽承载。

**违反它的后果(具体场景)**:若原生 HTTP 给每家写适配:SSE/工具调用/重试各写两遍,加第三家再写第三遍——降级链退化成多份代码的 if-else;且厂商报文差异只在切换那一刻暴露,而切换恰是最需稳的时刻:平时跑 DeepSeek 正常,一降级才发现解析层没覆盖 qwen-max 的某字段,演示当场翻车。若用两家官方 SDK:双客户端/双异常/双流式,降级逻辑被厂商细节淹没,dashscope SDK 自带依赖撑爆预算。若不采用兼容协议,"降级链"概念本身不成立——兼容格式的价值就是让多模型共享一份客户端。

**备选方案对比**:

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| 两家官方 SDK | 各自能力最全 | 双客户端/双异常/双流式,依赖超预算 | ❌ |
| 原生 HTTP 双协议适配 | 零依赖 | 解析/重试写两遍,切换时刻才暴露差异 | ❌ |
| openai SDK 单客户端,降级=换三元组 | 一份代码覆盖多模型/配置级降级/依赖可控 | 依赖厂商兼容承诺,解析层要打补丁 | ✅ 采纳 |

**关联**:ADR-011(按错误码判定降级)、ADR-008(阶段2 里程碑依赖本决策)、PRD-Core F012/F013/F025/F027-F033。

### ADR-008:代码六阶段推进,每阶段交付可运行里程碑

**状态**:已接受 | **日期**:2026-09-06 | **落点**:开发流程,覆盖 F001-F066 | **原则映射**:PRD 原则 6

**背景**:66 项功能分布在阶段0(总线)→1(脊柱)→2(模型加厚)→3(工具)→4(编排)→5(系统)→6(外壳)。实现策略候选:全部写完再集成(大爆炸)、先铺全量骨架再逐层填肉、按阶段门垂直切片。风险背景:复杂度集中在"循环 × 真实 LLM × 工具"的交互,一次写完无法定位故障层——是循环状态机错、报文解析错,还是工具超时?

**决策**:按阶段门推进:每阶段结束必须交付可运行/可演示/可测试的里程碑(PRD §4.6.2:阶段0 双插件互发+热卸载;1 CLI 对话→落盘→重启回放+guard 拒危险;2 流式+自动重试+401 降级;3 整理文件夹全自动;4 plan 批准后执行;5 FTS/compaction/fork;6 repair/CLI/Web/ACP)。阶段内功能按垂直切片:先打通一条端到端最小链路(如 阶段1 先跑通"输入→LLM→回话→落盘→回放"再补 guard/审批),再横向加宽。每阶段独立 pytest 目录与验收门,里程碑脚本 `scripts/demo_phase{n}.py`;INV-08 断言阶段 N 代码不得 import 阶段 N+1 模块。文档写最终态(66 项),代码按阶段生长。

**后果**:收益——①持续可用:每阶段都有可跑可录屏的实物,任何时刻项目都"活着";②风险早暴露:事件信封/seq 语义在阶段0-1 定死并验证,后面只加宽不翻地基;③回归边界清晰:坏了可定位到阶段,配合事件回放(ADR-001)归因;④演示脚本即验收门,防"写了没跑通"。代价——①阶段性重构不可避免(阶段2 动 llm 调用面、阶段5 动工具执行面),靠事件信封+错误码(ADR-011)+Definition 契约(ADR-002)吸收;②阶段门有纪律成本:未过门不许写下一阶段。

**违反它的后果(具体场景)**:若跳过阶段门直接写阶段4(编排):①agent-loop 三态机在并发 job 下状态错乱——返工从"改循环"扩大为"改所有依赖循环状态的代码",因阶段1 的循环被阶段4 的并发假设隐性改写;②阶段3 没做 spill 就去跑"整理 3MB 大文件夹",读入打爆上下文与预算,无法区分是工具没截断还是循环没预算闸——两层故障互相掩盖(PRD §4.6)。若大爆炸集成:复杂度一次性爆发,66 项互相牵连,错误无法归因到任何一层,数月无可用产物,任何方向修正(如事件 schema 调整)都全量返工。若先铺骨架再填肉:骨架期无真实 LLM,降级时序/审批交互/guard 顺序/背压全是假设,填肉期才逐个被打脸,返工面=全项目——假设错在接口层。

**备选方案对比**:

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| 大爆炸集成(写完再联调) | 只见一次集成 | 故障无法归因/数月无产物/修正即全量返工 | ❌ |
| 全骨架后逐层填肉 | 接口先行 | 无真实 LLM 验证,接口假设集体爆雷 | ❌ |
| 阶段门垂直切片,每阶段可运行 | 持续可用/风险早曝/可演示可录屏 | 阶段性重构,需稳定接口吸收 | ✅ 采纳 |

**关联**:PRD-Core §4.6/§4.6.2 里程碑表、ADR-010(脊柱先行=每阶段地基稳定)、ADR-011(错误码=跨阶段契约稳定)、INV-08。

### ADR-009:LLM 零信任——工具参数先验后跑(pydantic),校验先于执行

**状态**:已接受 | **日期**:2026-09-06 | **落点**:阶段1(F026)+阶段2(F027-F033) | **原则映射**:PRD 原则 4

**背景**:工具参数由 LLM 生成,而 LLM 无类型安全、无契约保证,且可被第三方内容(网页/文件/工具结果)注入。它可能缺字段、类型错、路径越界、甚至被诱导去读凭据文件。校验时机有四个候选:不校验直接跑、执行后校验、try/except 运行时兜底、执行前严格校验。约束:PRD 原则 4;审计要求"模型说了什么(raw_args)vs 实际执行了什么(强类型 args)"逐字段可比(INV-06);校验失败要能回喂 LLM 形成自纠闭环。

**决策**:零信任管道:tool_calls 的 raw_args(LLM 原始 JSON)→ **执行前**经 Definition.schema 做 pydantic 强类型校验(类型/必填/枚举/路径归一化)→ 再过 guard 链(ADR-003)→ 才允许调用 Provider。校验失败=结构化错误 tool.error(TLB-803)回喂 LLM 自纠;**不允许**宽容解析补默认值、部分参数透传、校验与执行间任何 try 降级。通过的强类型 args 与 raw_args 一并入日志(审计对照);输出侧同样校验,超长走 spill(F039)。Definition.schema 是唯一校验源,与 ADR-002 同源,不重复维护参数定义。

**后果**:收益——①非法参数物理上进不了执行,"格式错误执行"在门口被拦,副作用(删文件/写盘)永远不会先于校验发生;②校验失败成为闭环信号,模型收到 TLB-803 后可自我修正重试——这本身是阶段2 可演示的能力;③安全(guard)与正确性(校验)在统一入口分层实施,两道闸职责清晰。代价——①Definition.schema 必须权威且与实现严格一致,契约漂移=校验失真;②表达怪异但合法的参数可能被拒,靠错误回喂迭代,不靠放宽校验迁就模型。

**违反它的后果(具体场景)**:若执行后才校验或靠 try/except:文件写入/删除已发生才发现路径越界——校验晚于副作用,ADR-003 的前提被架空;LLM 输出 `{"path": 123}` 被 `str()` 隐式转换后去删"名为 123 的文件",类型错误绕过语义防线。若宽容解析静默补字段:模型学会偷懒,契约名存实亡,"模型说的参数"与"实际执行的参数"对不上,审计无法回答"那次删除到底用了什么路径"。INV-06 的 30 例畸形参数测试是守门员:断言真实函数零调用、args 逐字段一致。

**备选方案对比**:

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| 不校验直接 `**args` 展开 | 代码最少 | 类型错/越界/注入直通执行,裸奔 | ❌ |
| 执行后校验 / try-except 兜底 | 少一次转换 | 副作用先于校验,异常语义混杂 | ❌ |
| 执行前 pydantic 严格校验 + guard | 格式错误进不了执行/可回喂自纠/可审计 | 校验源需权威维护 | ✅ 采纳 |

**关联**:ADR-002(校验源=Definition.schema 单一来源)、ADR-003(guard 第二道闸)、ADR-011(TLB-803 结构化错误闭环)、PRD-Core §4.4/F023/F026/F039、INV-06。

### ADR-010:核心脊柱 8 模块不可换 vs 外围能力可插拔——边界判据

**状态**:已接受 | **日期**:2026-09-06 | **落点**:阶段1 定界,阶段3-6 持续适用 | **原则映射**:PRD §2.2 + 原则 2/3

**背景**:哪些模块进"核心脊柱"(每次对话必经、启动硬接线、插件不可卸载、卸载返回 BUS-002)?哪些挂 ctx.* 可插拔?两种错误方向都要防:外围升格脊柱=脊柱膨胀到不可维护;脊柱降格外围=安全/正确性裸奔。若无边界判据,全凭实现者手感,阶段推进中边界必然漂移。

**决策**:三条判据,满足任一即进脊柱:①**循环正确性依赖**:agent-loop 直接调用、错一次全错——三态机循环(F007)、scope 三闸(预算/轮数/窗口,F032/F025)、persistence 落盘(F011);②**跨能力共享契约**:总线两侧与所有能力都要看的形状——tools 注册表(F008)、llm 适配层(F012);③**语义不可降级替换**:替换=换架构而非换实现——session 真源入口(F009)、system-prompt 注入护栏(F010)。外围必须同时满足:可整体缺席(不装循环照跑)、可换实现(本地↔域、假↔真)、无状态或可由日志重建。脊柱依赖单向:agent-loop→{agent,llm,session,scope}、session→persistence、system-prompt→session(只读),禁反向依赖外围(外围经 ctx 注入);灰色带(compaction/fork)默认外围,升格需评审并记 ADR。

**后果**:收益——①脊柱稳定:阶段推进(ADR-008)的地基不塌,阶段3-6 全部功能只长在外围层;②外围自由生长:新能力=新包+注册,不触碰 core/;③可讲性:面试"骨架 vs 血肉"一句话讲清边界,评审问题简化为"挂 ctx 还是进脊柱"。代价——①边界靠纪律维护,每个新能力要过一道判据评审;②脊柱模块改动要过更严的回归(所有阶段测试都依赖它);③灰色带需要显式决策,不能靠默认。

**违反它的后果(具体场景)**:若把 Web 搜索/抓取当脊柱:一次外部搜索超时会卡死循环主路径——它本应是带超时/降级/spill 的外围工具,升格后把外部延迟写进了核心;若把 guard 降为外围:能力缺省=安全横切缺失,高危工具裸奔(ADR-003 前提失效);反之把斜杠命令升格脊柱:命令改动即触碰 core,脊柱随功能数线性膨胀,无人敢改。更隐蔽的违规:外围悄悄依赖另一外围实现(subagent import workflow 内部函数),绕过 ctx 注入纪律,卸载一个插件拖垮另一个——靠卸载测试与 import 方向检查(INV-08)拦截。

**备选方案对比**:

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| 无边界扁平(全按需 import) | 零抽象 | 新能力改核心/依赖网失控 | ❌ |
| 全脊柱(一切皆核心) | 无边界争议 | 脊柱膨胀,热插拔名存实亡 | ❌ |
| 判据三分 + 默认外围,脊柱只进 8 模块 | 地基稳/外围活/可讲清 | 边界需纪律评审 | ✅ 采纳 |

**关联**:ADR-002(三件套=外围机制载体)、ADR-004(注册表 enforce 边界,BUS-002)、TECH-ANCHOR.md、PRD-Core §2.2/§4.2。

### ADR-011:错误码为对外契约——失败不靠异常文本表达

**状态**:已接受 | **日期**:2026-09-06 | **落点**:阶段1(错误码基础),全阶段生效 | **原则映射**:PRD §3.7 错误码表(域前缀-NNN 风格)

**背景**:失败必然发生:配置错、网络断、限流、校验失败、guard 拒绝、超时、内部 bug。调用方多种多样:agent-loop 要决定降级还是终止,CLI/Web 要展示给用户,测试要断言,LLM 收到工具错误要理解并修正,审计要统计失败分布。若失败只以裸异常+文本表达,各消费方只能做字符串匹配——厂商文案一变、措辞一改,判断就断。PRD §3.7 已给出错误码雏形(EVT-100~106、TLB-803、BUS-002),本 ADR 把它确立为全局契约机制。

**决策**:全系统失败以稳定错误码表达,格式=域前缀-NNN(EVT 事件/TLB 工具校验/BUS 总线/CFG 配置/LLM 模型/SEC 安全/INV 内部),码表集中维护(ERR 文档);每码带分类(可重试/不可重试/需人工)、默认处置(降级/回喂/终止)、留痕要求。结构化错误携带 code+message+payload 跨模块边界传递(总线事件/工具返回/HTTP 响应),**不传裸异常**;未知失败归 INV 兜底,禁止现场发明新码不登记。降级链按码决策:401/429/超时→降级;TLB-803→回喂不降级;CFG-xxx→终止。

**后果**:收益——①消费方全部程序化:agent-loop 的降级/终止、LLM 自纠、前端提示语、pytest 断言都按码,不匹配文本;②错误即跨阶段契约:阶段1 定下的码,阶段6 Desktop 壳与 ACP 桥直接复用,接口稳定(呼应 ADR-008);③审计可统计失败分布(某工具被 guard 拒了多少次、限流集中在哪个时段)。代价——①初期要为每类失败起码并维护表,有命名与归类成本;②实现纪律:新失败不裸抛、不绕码;③过度分类风险,用 INV 兜底码吸收长尾。

**违反它的后果(具体场景)**:若无错误码只有异常文本:①前端判断"限流"要匹配文本,厂商文案一改判断就断,全链路变脆;②降级链(ADR-007)无法区分"参数错(重发白搭)"与"限流(稍等即可)",可能对参数错无限重试烧预算,或对限流错误放弃降级;③测试只能断言"抛了异常",无法断言"安全拒绝还是网络错",INV 测试失去精确断言对象;④跨阶段契约漂移:阶段2 新增的失败类型到阶段6 拿不到稳定标识,只能再猜文本;⑤面试"怎么知道该降级/重试/停"的标准答案=错误码分类。

**备选方案对比**:

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| 裸异常 + 文本匹配 | 零设计成本 | 文案依赖/无法程序化决策/跨阶段漂移 | ❌ |
| 每类失败一个自定义异常类 | 类型安全 | 类爆炸,跨模块序列化/文档/匹配都重 | ❌ |
| 域前缀-NNN 错误码表 + 分类 + 默认处置 | 稳定契约/按码决策/可统计 | 起码与登记有纪律成本 | ✅ 采纳 |

**关联**:ADR-007(降级按码判定)、ADR-009(TLB-803 回喂闭环)、PRD-Core §3.7/F 各错误路径、ERR 文档(码表权威清单)。

### ADR-012:外壳用 Windows 桌面程序(pywebview 壳 + FastAPI 同进程),不建 SPA、不开浏览器

**状态**:已接受(2026-09-06 修订:形态从"浏览器 Web"升级为"桌面程序") | **日期**:2026-09-06 | **落点**:阶段6(F061-F066 外壳项,Desktop/ACP) | **原则映射**:PRD 禁止表(React/44 包)+ 原则 5 + 用户拍板"要可视化桌面 APP"(2026-09-06)

**背景**:阶段6 外壳要交付 CLI、桌面程序、ACP 桥。用户明确要"Windows 桌面程序,双击图标开独立窗口"(可视化 APP),不要纯网页/浏览器标签页——面试演示双击 exe 的冲击力大于浏览器 URL。内核约束:禁止 TS/Node/npm 任何产物(React 44 包明令不做);单进程架构(ADR-005);FastAPI 单 worker 同进程。候选:React SPA、FastAPI 服务端渲染+浏览器访问、pywebview 桌面壳、PySide6 原生 Qt。

**决策**:**pywebview 桌面壳 + FastAPI 同进程本地服务**:双击 .exe(pyinstaller 打包)→ pywebview 打开独立窗口加载 `http://127.0.0.1:随机端口`(FastAPI 同进程,SSE 推事件);界面含会话列表/对话流/审批弹窗/**Agent 轨迹时间线回放面板**/预算仪表盘;前端原生 JS 或 Vue 打包产物,不开独立前端工程、无 node 构建链。窗口=只读投影(时间线=事件投影,ADR-001:页面永不直接写存储,写操作全走 session.append);CLI 与桌面共享同一引擎入口,ACP 桥复用 /api 协议语义。**关键架构不变式:桌面壳只是"浏览器"的替代呈现层——内核、API、事件流、投影纪律全部原样,形态升级不破坏单进程架构。**

**后果**:收益——①部署形态:PyInstaller 单 exe 双击即用,面试现场零部署零环境风险;②无构建链:改动即刷新,演示不依赖 node_modules;③窗口=只读投影,天然契合事件溯源——前端无状态所有权,关闭重开即重放;④**轨迹时间线面板把事件日志渲染成 Agent 干活过程的可视回放——事件溯源价值的最直观证明(面试展示主场景)**;⑤可答"为什么不需要前端框架":几个页面的复杂度配不上 SPA 的构建链成本。代价——①交互上限低于原生 Qt(不做拖拽级 UI),本就不在 66 项内;②前端需手工组织,量小可控;③SSE 断线重连:重连后从最后 seq 续拉,仍是投影语义;④pywebview 依赖 WebView2(Win10/11 自带,Win7 不支持——目标平台 Win11 可接受)。

**违反它的后果(具体场景)**:若上 React SPA:①引入 node/npm 构建链+双语言双仓库,撞禁止表,评审即不过;②Web 壳变独立部署单元(静态托管/CORS/联调),单进程架构(ADR-005)被从外壳打破;③为 3 个页面引入路由/状态管理/打包复杂度,与"外壳=可选演示层"定位不符;④演示依赖 node_modules,换机器当场失败。若 Web 直连存储不经 session 门面:读路径绕过真源入口,页面自持"第二份时间线",违反 ADR-001 投影纪律。

**备选方案对比**:

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| React SPA 前端工程 | 交互上限高、生态大 | 禁止表/构建链/双部署单元/演示环境风险 | ❌ |
| PySide6/PyQt6 原生 Qt | 最"原生桌面" | 学习曲线陡(2-4 周),轨迹可视化要 Qt 画布重画,求职增量小 | ❌(用户对比后弃) |
| 页面直连存储(不经 API/门面) | 实现最快 | 绕过真源入口,第二份状态,违反 ADR-001 | ❌ |
| **pywebview 壳 + FastAPI 同进程 + 原生 JS/Vue + SSE** | 单进程零破坏/投影语义/零构建链/**HTML 做轨迹时间线最容易/复用用户 Vue 技能**/双击 exe 演示 | 交互上限低于 Qt,需手写前端 | ✅ 采纳 |

**关联**:ADR-005(单进程不被外壳破坏)、ADR-001(页面=事件投影,刷新即重放)、ADR-011(/api 响应复用错误码)、PRD-Core §2.1 外壳层/阶段6。
